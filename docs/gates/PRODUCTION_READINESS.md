## 1. What production ready means (affirmative definition)

AEGIS NIDS Windows is production ready **only when all of the following are
true at the same build source commit** (`git_source`, ADR-0008):

1. `tools/truth.py verify` → `TRUTH_VALID`; machine maps carry the build source
   commit and source paths are clean.
2. Component audit PASS (66/66 modules, 0 production failures, Part II 5/5).
3. A **current-source 24 h soak** PASS: `--baseline auto` start, hourly rechecks
   against the saved baseline, `--hours 24`, budgets `--loss-budget 3500
   --shed-budget 20000`, no problems, no counter regression, no restart, no
   degraded health. Older windows at other source commits do not count.
4. `tools/host_preflight.py` PASS on the clean host (drivers Valid, 4/4 services
   RUNNING, topology PASS, duplicate-pair probe recorded).
5. Release signature verifies on the **current candidate**
   (`release/T20-final/b597e71`) with the owner-approved anchor
   `txigrGWzVRf/zJ3OGdrctW2eBqqy18LOJv6dY5keJ6o=`; `waivers.json` empty.
6. `tools/release_engineering.py --verify` → all recorded digests match.
7. `tools/evidence_debt.py` → 0 new unnamed product files; `check_summary.py`
   → `SUMMARY_VALID`.
8. Upgrade/rollback drill PASSED and service returned to RUNNING.
9. Driver signing decision recorded. Current drivers are **test-signed**; HLK /
   production signing is a separate decision, not implied by a green gate.

## 4. On-call and incident handling

### During the release window (RB-024)

- **Owner of the window:** the operator who started the soak. Only that owner
  may extend, void, or restart it. A restart is a one-time, owner-approved
  action and voids all prior windows for this source commit.
- **Watcher:** `admin-evidence/e5-clean-host-20261119-final/soak-watch-f4cde3c-v2.ps1`
  performs hourly read-only rechecks, copies each JSON to a timestamped
  `soak-24h-f4cde3c-delta-*.json`, writes `soak-24h-f4cde3c-latest.json`, and
  stops on any problem/FAIL. It runs **detached** (PID recorded in
  `soak-watch-f4cde3c.status.txt`) so it is not bound to the agent harness
  command timeout; a lightweight `soak-wait-terminal.ps1` resumes the operator
  at PASS/FAIL. The original `soak-watch-f4cde3c.ps1` was terminated by the
  harness's 1-hour timeout at 05:38 — this is a **watcher-tool interruption,
  not a soak failure**: no service, topology, load, or counter state changed,
  and checks at 04:38 (`...-0438.json`) and 05:39 (`...-0539.json`) are intact.
  Never treat the log gap as detection loss or as voiding the window.
- **Escalation triggers:** any service not RUNNING, daemon restart/uptime
  regression, `health.state == DEGRADED`, any loss/shed counter regression vs
  the baseline, `problems[]` non-empty, or a verdict of FAIL.
- **Action set:** stop the watcher, preserve the failing artifact, do **not**
  claim PASS, do **not** tag/publish, and apply RB-024 "Failure handling".
  Do not install/restart services, switch topology, or inject load to "fix" a
  running window — that invalidates it.
- **Void ≠ failure:** windows voided by owner/decision are recorded as voided,
  not as failures and not as release proof. Keep the void record.

### Steady state (after release)

- `RB-006` subsystem health check — first response to a health alert.
- `RB-007` performance tuning — queue depth / batching saturation.
- `RB-008` SIEM ingestion debug — forwarding/spool failures.
- `RB-002` / `RB-003` — forensic query and audit-tamper investigation.
- `RB-004` / `RB-005` — snapshot restore and config rollback.
- There is no pager/MTTD/MTTR definition today; escalation is operator-driven.
  Defining an on-call rotation is a future owner decision, not a gate.
