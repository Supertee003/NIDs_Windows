# CLI-STATE-001 — the daemon's state machine is now named, not hidden

**Created:** 2026-11-14
**Build source:** unaffected — the patch is `tools/` and `tests/` only, no
`RUNTIME_PATHS` entry, so the running 24 h window stays valid.

---

## 1. Root cause of DEFECT-READY-001 (fixed cause, open defect)

Reading the raw daemon payload through `tools/probe_control_pipe.py` — the bytes
the pipe actually returns, not the CLI's rendering — showed the contradiction is
between two fields the daemon owns:

```
"state":"RUNNING","runtime_state":"DEGRADED","degraded":false,
subsystems 7/7 RUNNING, workers all ready, data_integrity all zero
```

* `state` is the **health contract** (`healthJson`, `src/control/state_machine.zig:309`),
  computed from live facts: every subsystem healthy, `workers.pipeline`,
  `bridge_ready`, and the data-loss counters against the budget.
* `runtime_state` is the **lifecycle state machine**, set once in
  `src/daemon.zig:854-860`:

  ```zig
  if (state.g_pipeline_ready.load(.acquire) and !pipeline_failed and bridges_ready) {
      runtime_sm.g_runtime.transition(.running);
  } else {
      runtime_sm.g_runtime.transition(.degraded);
  }
  ```

  `bridges_ready = bridge_init.allActive()` is sampled **once**, immediately
  after `bridge_init.initAll()`. If a bridge is not yet attested at that instant
  the runtime is moved to `.degraded` and **nothing ever re-promotes it**:
  `recomputeHealth()` only handles `failed → degraded` and `degraded →
  recovering`, and no timer calls it.

So the defect is a one-shot startup evaluation with no promotion path, and the
operator sees the stale half.

## 2. What this slice changes (CLI only, fail-closed kept)

`tools/aegisctl/api/control_api.py`

* computes `state_machine_disagrees` = `runtime_state == DEGRADED` **and** the
  health contract says `state RUNNING`, `degraded false`, all six workers ready,
  and every subsystem RUNNING;
* exposes `state_machine_state` and `state_machine_disagrees` in the payload;
* **keeps** the merge fail-closed: a degraded lifecycle still makes
  `state` DEGRADED and `degraded` true. The patch changes the explanation, never
  the verdict.

`tools/aegisctl.py`

* `build_readiness` emits `state_machine_degraded_but_health_facts_ready` when
  the flag is set, and counts that as a *named* degradation, so
  `degraded_without_named_component` no longer appears;
* `readiness` now also reports `state_machine_state` and `state_machine_disagrees`;
* `status` and `diagnose` print a second `State machine:` line plus an explicit
  `[!]` note with the defect id.

## 4. Limitations

1. **The daemon still reports a stale lifecycle.** This slice improves the
   report; it does not promote the state machine. The real fix is in
   `src/daemon.zig` (+ a promotion path), blocked by the running soak.
2. **The gate still refuses.** `readiness` remains `ready:false` — deliberately,
   because a runtime whose own two states disagree is not ready in the sense the
   gate means.
3. **E4 here is a CLI-surface reading.** It proves the operator surface names the
   cause on a live daemon; it proves nothing new about daemon behaviour.
4. **`state_machine_disagrees` is a heuristic over published facts.** A new
   degraded condition that the health contract does not expose would be missed;
   the tests pin the four live cases only.
