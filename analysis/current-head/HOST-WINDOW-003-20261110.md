## 6. #29 threshold: **not met at 4,000; zero loss measured at 3,229**

The owner accepted **zero drops at sustained 4,000 file-ops/s**. One file-op is a
complete open+write+close+unlink of a distinct file, so the rate is measured from
completed op-sets (`soak_rate.py`).

| Run | Achieved op-sets/s | Duration | Drops (per source) | Verdict |
|---|---|---|---|---|
| smoke, 2 workers | 3,012.7 | 5 s | 0 | measured-path check |
| 1 worker | 2,484.2 | 60 s | 0 | **zero loss** |
| 2 workers | 3,229.5 | 60 s | 0 | **zero loss** |
| 3 workers | **4,008.6** | 90 s | **15,989 `capture_etw` / `fim_change` + 1 `reg_change`** | **threshold NOT met** |

At 4,008.6 op-sets/s the pipeline shed **15,990 rows**, all on the duplicate ETW
FIM lane; the minifilter lane lost nothing
(`capture_fim.push = 1,455,134, dropped = 0`). That is the same lane the
2026-11-09 sweep blamed, re-observed on the deployed build.

**Correction to the first version of this section.** The first 4,000 run reported
`zero_drops: true` because the harness read `data_integrity` the instant the
generator stopped, and that block is a periodic snapshot: the drops landed after
the read. The soak gate then failed ten minutes later with
`queue_dropped_total = 15990`. The harness now polls until the counter is stable
across two reads and takes attribution from the live `queue.stats` buckets. The
claim in the earlier commit message ("4,008.6/s sustained with zero delta") was
wrong and is retracted here; `rate-4000-90s.json` is kept as the historical
first attempt.

Consequences:

- The owner-accepted 4,000 op-sets/s threshold is **above this build's zero-loss
  ceiling**, which is bracketed between 3,229 and 4,009 op-sets/s.
- #29 therefore stays open. The open work is the ETW duplicate lane (either stop
  producing the duplicate, or raise its share), not the minifilter ingress.
- `HOST-WINDOW-003` cannot claim a clean soak on this process: it carries the
  15,990 drops and reports `DEGRADED`, which the gate reports correctly
  (`soak-attempt.json`, exit 3).

## 7. Reboot (R-06 / FREEZE #22) — **deferred by the operator**

Both telemetry drivers are `DEMAND_START` **by design** (a lab host should not
grow kernel surface at every boot) and had no loader, so a reboot used to leave
the product partially blind. The owner chose to keep the start mode and add a
loader:

- scheduled task `AegisBootSequence` — trigger *At system start up*, 20 s delay,
  run as `SYSTEM` (highest), executes `boot-sequence.ps1`;
- the script starts `AegisWfp` then `AegisMinifilter` with retries and restarts
  `AegisNids` **only** when a driver was down at boot, so a normal manual restart
  is not disturbed;
- it writes `post-boot/post-boot-probe.json` (service states, deployed hashes,
  SCM `7031`/`7034` since `LastBootUpTime`, daemon status).

Verified registered (`task-query.txt`): `Status: Ready`, `Schedule Type: At system
start up`, `Run As User: SYSTEM`. The task was initially invisible to a
non-elevated `schtasks` query — a real usability defect, since an operator could
not tell whether the loader existed — so its security descriptor was amended to
grant Users read+execute.

**The reboot itself did not happen.** The elevation prompt for `reboot.ps1` was
declined twice (2026-11-10 14:28 and 14:30), so the boot path is *prepared and
readable* but **not proven**, and the 24 h soak has not started. What is needed is
one approved elevated action: either run
`admin-evidence\host-window-003-20261110\reboot.ps1` elevated, or
`restart-daemon.ps1` if only a clean counter set is wanted.
