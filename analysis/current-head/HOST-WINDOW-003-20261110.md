## 6. #29 threshold, owner-approved and measured

The owner accepted **zero drops at sustained 4,000 file-ops/s**. One file-op is a
complete open+write+close+unlink of a distinct file, so the rate is measured from
completed op-sets, not assumed from a sleep interval
(`soak_rate.py`, transcript `rate-4000-90s.json`):

```json
{"target_ops_per_second": 4000, "seconds": 90.0, "op_sets": 360777,
 "achieved_ops_per_second": 4008.6, "target_met": true,
 "health_before": "RUNNING", "health_after": "RUNNING",
 "loss_deltas": {}, "zero_drops": true}
```

- 360,777 file op-sets in 90 s → **4,008.6/s sustained**, above the accepted floor.
- Zero delta on `queue_dropped_total`, `minifilter_pipeline_dropped`,
  `minifilter_ring_dropped`, and all three Nose counters.
- Health stayed `RUNNING` throughout; no SCM `7031`/`7034` in the four hours
  covered by the window (`scm_7031_since_4h=0`).

A smoke run (`rate-smoke.json`, 2 workers, 5 s) preceded it to validate the
measurement path at 3,012.7/s.

## 7. Reboot (R-06 / FREEZE #22)

Both telemetry drivers are `DEMAND_START` **by design** (a lab host should not
grow kernel surface at every boot) and had no loader, so a reboot used to leave
the product partially blind. The owner chose to keep the start mode and add a
loader rather than flip the drivers to `AUTO_START`:

- scheduled task `AegisBootSequence` — trigger `AtStartup`, 20 s delay, run as
  `SYSTEM` (Highest), executes `boot-sequence.ps1`;
- the script starts `AegisWfp` then `AegisMinifilter` with retries, and restarts
  `AegisNids` **only** when a driver was down at boot (so a normal manual restart
  is not disturbed);
- it writes `post-boot/post-boot-probe.json`: service states, deployed hashes,
  SCM `7031`/`7034` since `LastBootUpTime`, and the daemon's own status.

The reboot was requested at the end of this window so the operator does not have
to hand-load the drivers. Post-reboot verification and the 24 h soak are recorded
in the continuation of this file.

## 8. What this window does **not** prove

- #30 is not closed: no crash-free interval has been *observed* yet. The fixed
  helper is now the one on disk, which is the precondition, not the proof.
- The 4,000 op-s/s result is one 90 s run, not the 24 h soak. It meets the
  accepted threshold at that rate; it does not prove a day of stability.
- `readiness` still refuses with no named cause (S1-05 remainder).
- No signing key material was involved, so E7 remains unreachable (FREEZE-001 §3.1).
