# R1005-HOSTS-E5 — hosts path rule fires on the host (open, not only write)

**Created:** 2026-11-14
**Measured on:** installed `680510ABB14E328A826B8E4151867F2D0657783BAD1CB29881FBD4A0F0377B3A`
(source `e4c2188`)
**Canary:** `Get-Content C:\Windows\System32\drivers\etc\hosts` (read-only, no
modification), then `aegisctl alerts --limit 5000 --json`.
**Level:** E5 (host, installed image hash-asserted, live read).

---

## 1. Result

The alert scan (anchored at the ring tip, ALERT-SCAN-001) returned:

```json
{
  "rule_id": "R1005",
  "name": "hosts File Modification",
  "severity": "High",
  "action": "Block",
  "source": "file_sensor",
  "payload_len": 58,
  "record_seq": 231465,
  "verified": true
}
```

Five R1005 records were captured (seq 231465-231469 and 232488, payload 58 and
99 bytes), plus two R1001 `System32 Write Attempt` records (payload 42) and the
usual R1004 DLL noise (677). The read did **not** modify hosts.

## 2. What this proves

- The hosts path is visible through the minifilter lane and reaches the rule
  engine; the earlier "R1005 = 0" was the alert-scan defect, not a missing
  detection.
- R1001 also fires on the same lane for System32 paths.
- The forensic records carry a payload (58/99 bytes), so the path is no longer
  a zero-length claim.

## 3. The false-positive class this exposes

R1005 is named "hosts File **Modification**" and R1001 "System32 **Write**
Attempt", but both fired on a **read**. The minifilter registers
`IRP_MJ_CREATE` for every open, including read-only opens, and the rule engine
matches the path without an operation filter. So:

- a user or service reading `hosts` raises a High/Critical "modification"
  alert;
- reading a System32 DLL raises "write attempt".

This is an over-broad path match, not a miss. It is recorded as a detection
quality defect; the correct fix is to carry the desired-access/operation in the
event (or emit a distinct `file_open` kind) and evaluate write-oriented rules
only for write/create-new.

## 4. Detection-only confirmation

`aegisctl enforce status` on the same host:

```json
{"enforcement_mode":"detection-only","gate_source":"closed",
 "host_effect_capable":false,"host_effect_confirmed":false,
 "prevention_gate":"closed","tier3_enforcing":false}
```

The alert's `action: "Block"` is the **catalog intent**, not a host effect.
`authority` reports `HELD`; no block occurred.

## 5. Limitations

- One host, one read canary.
- The R1004 rule is extremely noisy (677 records in the same window); a
  `--rule` filter is still needed for ergonomic canary verification.
- Operation-level filtering (read vs write) is not implemented; this is the
  next detection-quality slice.
- Forensic retention is ~16k records; the anchored scan and `--limit 5000`
  were required to see these records.
