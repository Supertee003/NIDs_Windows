Windows event log, `2026-11-16` local time (UTC+07):

|---|---|---|
| 01:44:53 | Kernel-Power 109 | the kernel power manager initiated a shutdown transition |
| 01:44:54 | Kernel-Power 577 | the system prepared for a system-initiated reboot from Active |

| 01:45:06 | Kernel-Boot 20 | the last shutdown's success status was true |

The shutdown was clean ("success status was true"), there is no BugCheck, and
the AegisNids service came back RUNNING on its own with a new PID (22468 ->
23072). This is a host lifecycle event, not a daemon crash. The cause of the
system-initiated reboot was not captured in the log window examined
(`Kernel-Power` does not name an initiator here); it is consistent with a
servicing/update restart, but that is an inference and is labelled as one.

What follows for the measurement: the loss counters are process-lifetime
totals. After the restart they reset and re-accumulated, so the absolute values
at the gate (`queue_dropped_total` 1,377, `shed_overload` 984, both inside the
3,500 / 20,000 budgets) describe the **post-reboot** process only. They cannot
be compared with the pre-reboot ledger as one window.
