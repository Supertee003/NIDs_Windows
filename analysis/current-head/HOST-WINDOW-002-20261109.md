## 7. KIND-ATTR-001 — minifilter FIM records ingress as `packet_captured`

Observed while reading the D3 attribution, then confirmed in source:

- `minifilter_reader.submitRecord` builds the event with `canonical.create(.minifilter)`,
  which sets `event_type = .custom` and never changes it.
- `event_queue.pushDecodedFrame` maps `.custom => .packet_captured`, and its
  switch has **no branch that yields `.fim_change`**.

Consequence: 300,992 of the 300,995 `capture_fim` events in the heavy burst are
counted (and delivered) as kind `packet_captured`, with a file path in the
payload. The ETW lane tags the same churn correctly, so the two sensors disagree
about the kind of the same activity, and any consumer keyed on `fim_change`
cannot see minifilter records at all.

Not fixed in this patch, deliberately: the obvious repair (map `.minifilter`
to `.fim_change`) would send a second, duplicate FIM stream into every
correlator and rule keyed on `fim_change` — the ETW lane already carries it —
which is a loss/duplication decision (issue #29 territory), not a typo fix. The
decision this needs is written down in DEV-PLAN §3.5, not silently applied.

## 8. READINESS-001 — start order decides RUNNING vs DEGRADED

After the corrected install the daemon reported `state: DEGRADED` while all
seven subsystems reported RUNNING. The startup log names why:

```
1794251880 [warning] [WFP TELEMETRY] kernel read provider unavailable; ...
1794251880 [info] [CAPTURE] network acquisition mode=none reason=no_source packet=false kernel=false
1794251880 [warning] runtime degraded: required bridge dependency is unavailable
```

The daemon was started by the installer at a moment when the WFP driver was
still Stopped, so `bridge_init.allActive()` was false and `daemon.zig` took the
`transition(.degraded)` branch. **The state is decided once, at startup, and is
never re-evaluated when the bridge appears later** — so drivers-then-daemon and
daemon-then-drivers end in different advertised states for the same machine.

Restarting `AegisNids` with both drivers already Running:

```
state: RUNNING          (7/7 subsystems RUNNING)
1794253255 [info] Npcap pinned device via AEGIS_DAEMON_IFACE: \Device\NPF_{CE375996-...}
1794253255 [info] Npcap capture loop starting
1794253263 [info] registry change matched rule 2: HKLM\SYSTEM\CurrentControlSet\Services
```

and, 25 s later, `pushed_total 18838, dropped_total 0` with all five sensors
feeding: `capture_wfp` 6,762, `capture_etw` 6,814, `capture_fim` 5,251,
`capture_registry` 9, `capture_host_net` 2.

Operational consequence for `HOST-WINDOW-001`: D2's order must be
**drivers first, then restart the daemon**, otherwise a correctly installed host
advertises DEGRADED forever. The soak clock starts at that restart
(`2026-11-10T02:40:55`), not at install time, and `tools/host_soak_check.py
--start auto` is what turns R-08's 24 h criterion into a pass/fail instead of a
memory.

## 9. D4 — page heap cycles (#30, R-08)

Prerequisites checked first: `gflags.exe` and `cdb.exe` exist under Windows Kits
10.0.28000.0 `Debuggers\x64`, and WER `LocalDumps` is configured (`DumpFolder
D:\NIDs_Windows\admin-evidence\e5-host-proof-20261026\wer-localdumps`,
`DumpType 2`).

| Attempt | Setup | Result |
|---|---|---|
| 1 | `gflags /p /enable aegis_nids.exe /full`, then `sc stop` + 2 s sleep + `sc start`, 6 s poll | **aborted at cycle 1**: the start raced the still-stopping service, the process never launched, and the abort path left `AegisNids` Stopped until it was started by hand. No data, no dump |
| 2 | same page heap, but wait for SCM `Stopped` (≤30 s) before `sc start` and poll `Running` (≤40 s), control-plane probe per cycle, page heap disabled and service restored in a `finally` | **10/10 cycles RUNNING**, control plane answering RUNNING each time, 3.3–6.2 s per restart, **0 new dumps** |

So full page heap did not reproduce the #30 heap corruption across ten
start/stop cycles on the deployed build. That is a negative result, and it is
recorded as one: the root cause is still unnamed, so R-08 cannot close. What the
cycles do establish is that a page-heap-instrumented daemon survives restart
repeatedly — the crash needs a trigger that start/stop alone does not produce.

Transcript: `admin-evidence/host-window-20261109/d4-pageheap-cycles.txt`
(gitignored; the durable statements are the table above).

Lesson recorded because it cost a minute of host downtime: an abort path that
disables instrumentation must also restore the service. Attempt 1's `finally`
block only disabled page heap after the loop, and the loop exited after the
first failed cycle.
