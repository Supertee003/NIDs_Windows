# SIGN-RELEASE-001 — the signature gate had no way to produce its own artifact

**Created:** 2026-11-14
**Build source:** `tools/`, `tests/` and `release/` only — no path in
`RUNTIME_PATHS`, so the running 24 h soak stays valid.
**Level:** E7 for the artifact itself (a detached ed25519 signature over the
release `SHA256SUMS`), E2 for the tool.

---

## 1. What was blocked

`release_signature` demanded a `signatures.json` beside `SHA256SUMS` carrying
`signature`, `public_key` and `signed_digest`, and it recomputes
`sha256(SHA256SUMS)` to check the record. The repository had:

* `release/T20-final/46b93dc/signatures.json` — four informational fields
  (`policy`, `immutable`, `commit`, `shipped_files`), no signature at all;
* `rust-src/bin/aegis_keygen.rs` — a standalone keygen with no crate, built by
  nothing;
* `src/policy/policy_signing.zig` — ed25519 for *policy* objects, not for a
  release tree.

So the gate could never pass, whatever the owner did with the build.

## 2. What was added

`tools/sign_release.py`:

* `--generate-key PATH` writes a raw 32-byte ed25519 seed with mode 600 and
  prints **only** the public key and the path;
* `--sign --dir D --key-file K` signs the bytes of `D/SHA256SUMS`, records
  `signature` (base64), `public_key` (base64 raw 32 bytes), `algorithm:
  ed25519`, `signed_digest` (uppercase SHA-256 of those bytes), `signed_file` and
  `signed_at`, and preserves every other field already in `signatures.json`;
* `--verify --dir D` recomputes the digest, checks it against the record, and
  verifies the signature over the same bytes.

The private key never leaves the machine, is never printed, and `.keys/` is
gitignored. What the signature covers is stated in the module docstring: the
sha256 the gate checks is the digest of exactly the signed bytes, so a changed
`SHA256SUMS` fails on the digest before the signature is even considered.

`tests/tools/test_sign_release.py` (9 pins) asserts against the gate's own
evaluator — `tools/final_audit.evaluate_signature` — rather than a restatement of
its rules, and covers the fail-closed cases: tampered `SHA256SUMS`, flipped
signature byte, unsigned record, missing record, wrong algorithm, and the shipped
reference record (which must be rejected).

## 5. Limitations — what this signature is and is not

1. **It is a software signature by a key on this host.** It proves the tree was
   not altered after signing; it does not prove who the signer is beyond the key
   itself, and there is no certificate, timestamp authority or HSM.
2. **The private key is `.keys/aegis-release.ed25519` on this machine only.**
   If it is lost, this release cannot be re-signed with the same identity; if it
   leaks, the signature means nothing. Back it up offline and record the public
   key (`txigr...J6o=`) somewhere that outlives the machine.
3. **The signed tree reflects the artifacts as they are in `dist/` at assembly
   time**, not a fresh build of every component. `RC PASS` verifies the tree
   against `build_manifest.json`; it does not rebuild it.
4. **A commit that touches `src`, `nose`, `brain`, `ts_policy`, `shared`,
   `contracts`, `drivers`, `go`, `build.zig`, `CMakeLists.txt`, `Cargo.toml` or
   `rust-src` after 2026-11-14T22:20:15 invalidates the running soak** and the
   signature must be re-made over a re-assembled tree. Records, tests and tools
   are outside that set.
