# LOSS-BUDGET-001 — a loss budget the runtime actually honours

**Created:** 2026-11-13
**Build source before this patch:** `a9dd914`
**Finding:** RC-CLOSEOUT accepted a 3,500/4,000 loss envelope, but the runtime
still reported DEGRADED for any nonzero counter, so `readiness` stayed false
and `host_soak_check --loss-budget N` could not pass: the tool checks
`health.state` independently of the budget.
**Level:** E2 + E5 (env read on the host is the E5 half).

---

## 1. The contradiction this closes

`RC-CLOSEOUT-20261113` accepted:

```
queue_dropped_total <= 3,500 / 24 h
shed_overload      <= 4,000 / 24 h
```

but `state_machine.zig` computed:

```
data_loss_observed = queue_drops != 0 or ... minifilter_pipeline_dropped != 0
```

So the 25.33 h window (2,900 / 3,357, both inside the envelope) reported
`state=DEGRADED`, `degraded=true`, and `readiness` exit 1. A budget the
operator must pass to the soak tool while the daemon ignores it is not a
budget; it is a documented contradiction.

## 2. What changed

- `src/pipeline/runtime_state.zig`:
  - `g_loss_budget` (atomic u64, default **0**);
  - `parseLossBudget(value)`: unset/empty/invalid/negative -> 0, valid decimal
    -> that value; whitespace trimmed;
  - `initLossBudgetFromEnv()` reads `AEGIS_LOSS_BUDGET` once at startup.
- `src/daemon.zig`: calls `initLossBudgetFromEnv()` at startup and logs the
  effective budget.
- `src/control/state_machine.zig`:
  - every `data_loss_observed` comparison is now `counter > budget` instead of
    `counter != 0`;
  - the health payload's `data_integrity` block gains `loss_budget`, so an
    operator can see which envelope the daemon is honouring.
- Default **0 preserves the previous strict behaviour** exactly; no existing
  deployment changes until the env var is set.

## 3. Semantics and limits

- The budget is **per counter**, not a shared pool. `AEGIS_LOSS_BUDGET=4000`
  allows up to 4,000 rows in each of queue/nose/ring/pipeline counters.
- `shed_overload` is not in the health `data_integrity` block (it lives on
  `queue.stats`); the daemon budget does not cover it. The soak tool's
  `--shed-budget` remains the separate gate.
- The budget is read once; changing it requires a service restart. It is not
  hot-reloaded and cannot be raised by the control plane.
- An invalid or negative value falls back to 0 (strict), never to unlimited.

## 5. How to deploy the envelope

The service must see the variable. Windows services do not inherit a shell
env, so the deploy window sets the service `Environment` value and restarts:

```powershell
reg add "HKLM\SYSTEM\CurrentControlSet\Services\AegisNids" `
  /v Environment /t REG_MULTI_SZ /d "AEGIS_LOSS_BUDGET=4000" /f
sc.exe stop AegisNids
sc.exe start AegisNids
```

Then `aegisctl health` must show `data_integrity.loss_budget = 4000`, and the
daemon must stay `RUNNING` while counters are at or below 4,000. A counter
above 4,000 must return `DEGRADED`, which is the strict path and is pinned by
the unit test.

`host_soak_check.py` should be run with the matching numbers:

```powershell
python tools/host_soak_check.py --start auto --hours 24 `
  --loss-budget 4000 --shed-budget 4000
```

## 6. What this does not do

- It does not eliminate the 0.026 % loss; it makes the accepted envelope
  operational.
- It does not cover `shed_overload` in health; the soak tool counts that
  separately.
- It does not ship the variable: `tools/installer.py` and the service creation
  path still need to write `AEGIS_LOSS_BUDGET` for a fresh install
  (packaging gap, same class as the boot-task gap).
- It does not make the daemon E7 or fleet-qualified.
