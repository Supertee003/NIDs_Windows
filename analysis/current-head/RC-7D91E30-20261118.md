## Why `bece8f1` was rejected

The first elevated RB-024 attempt installed the `bece8f1` bundle. The two
user-mode services came up, but the kernel telemetry drivers did not:

```
AegisWfp        STATE : 1 STOPPED   WIN32_EXIT_CODE : 577 (0x241)
AegisMinifilter STATE : 1 STOPPED   WIN32_EXIT_CODE : 577 (0x241)
```

`0x241` is `ERROR_INVALID_IMAGE_HASH`. `Get-AuthenticodeSignature` reported
`NotSigned` for the images in `C:\Windows\System32\drivers` and for
`release/T20-final/bece8f1/drivers/*.sys`. The unsigned bytes came from the
current WDK outputs in `build/x64/{wfp,minifilter}`; the assembler copies those
paths verbatim, so `RC PASS` could not detect the defect. An older tree
(`release/T20-final/7234d7a`) proved that this host accepts the same two test
certificates that are already present and trusted here.

This was a packaging defect, not a source, policy or authority change. No
certificate was generated, imported or promoted, and no enforcement was
enabled. Build source stays `4169839`, so the machine maps remain valid.

## Corrective patch

1. Confirmed the unsigned WFP SHA-256 against the pinned value in
   `scripts/sign_wfp_driver_20261024.ps1`, then re-signed
   `build/x64/wfp/aegis_wfp.sys` with the existing pinned certificate
   `00E92849867308596564D134BB981EF726798E97`.
2. Re-signed `build/x64/minifilter/aegis_minifilter.sys` with the existing,
   already machine-trusted certificate
   `60B05537FEB7A40D6F6624FF5C005C09DC245A63`.
3. Verified both images report `Status=Valid`, then repackaged the installer
   from the same build output and reassembled + signed the candidate tree.
4. Verified the candidate's own driver copies are `Status=Valid` and that
   `sign_release.py --verify` passes with the owner-approved anchor.

Commands and raw output are in
`admin-evidence/e5-clean-host-20261118-final/driver-signing.log` and
