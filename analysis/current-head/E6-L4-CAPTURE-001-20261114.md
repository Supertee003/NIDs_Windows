# E6-L4-CAPTURE-001 — the rule path is empty and loopback is not what this install captures

**Created:** 2026-11-14
**Build source:** unaffected; `tests/` only.
**Level:** E4 live measurement, **negative result** for the rule path, plus a
correction to a gate I wrote earlier in this session.

---

## 1. What was being tested

`configs/Rules.json` ships 23 rules, three of them L4 with a real rate
configuration:

```
R9006  TCP SYN Stealth Scan   layer L4  rate_mode distinct_dst_ports
                              rate_threshold 20  rate_window_ms 10000
R9002  ICMP Flood             rate_mode count, threshold 50 / 1000 ms
R9007  TCP XMAS Scan          per-packet FLAGS predicate
```

`src/pipeline/event_processor.zig:307` evaluates them when
`ev.source == .capture_npcap`, and canonical Go-Nose frames map to exactly that
source (`event_queue.zig` → `legacySourceFor`), so the path exists for
production traffic. A 150-port loopback SYN scan exceeds R9006's threshold
several times over inside its window.

## 2. Measurement — no rule ever tags a record

```text
forensics list (1000 retained records):  0 with rule_id != 0
150-port scan, then --after <head>:
  187 new records  → rule_id histogram {0: 187}
  by source: host_telemetry 121, file_sensor 36, npcap_sensor 30
```

Repeated three times with the same result: the live evidence stream contains no
rule-tagged record at all, and the scan adds none.

**Caveat that belongs beside the number:** this install does not capture
localhost traffic. Two 5 s windows measured in sequence:

```
idle              162 npcap_sensor records / 5 s
during the scan    87 npcap_sensor records / 5 s
```

So the scan itself never reached the sensor, and the measurement proves "no
rule-tagged record exists in the live stream", **not** "R9006 is broken". The
honest statement is narrower than the first version of this note.

Consequences recorded:

* `DETECT-L4-001` (OPEN) — the L4 rule path is unproven and, as far as this host
  can show, never tags anything. `GAP-L4-FLAGS-LIVE-UNPROVEN` already said the
  flags lane was unproven; this narrows it to "no rule hit observed at all".
* `CAPTURE-LOOPBACK-001` (OPEN) — a self-test on loopback cannot feed detection
  on this install; detection gates need a lab interface (VMnet, as the earlier
  R9006 evidence used).

## 3. Correction to my own E4 gate

`test_real_loopback_traffic_reaches_the_ring` asserted

```python
assert after_packets >= before_packets
assert after_ring >= before_ring
```

Those pass on an idle host. A check that cannot fail is not evidence, and I wrote
it. It is replaced by `test_the_sensor_keeps_writing_evidence`, which measures the
sensor's own record stream over three consecutive windows and fails if all three
are empty — and whose docstring states the attribution failure and the gap ids.

## 5. Limitations

1. **This is a negative measurement, not a diagnosis.** It does not say whether
   the flags lane is empty, the rate window is mis-keyed, or the installed binary
   predates the flags commit. Those are three different fixes.
2. **Loopback is not captured**, so nothing here was injected into the sensor on
   purpose. A lab-interface rerun is the only way to ask the detection question
   properly, and it changes a VM network — out of scope for this window.
3. **No claim about L7.** The four L7 rules (R0056 SQLi and friends) need payload
   bytes; whether those reach the AC on the canonical path was not measured here.
4. **`xfail` is a tripwire, not a fix**, exactly as with `DEFECT-READY-001`.
