# E6-L4-CAPTURE-001 — the rule path is intermittent, loopback is not captured, and two of my own gates were unsound

**Created:** 2026-11-14 (updated same day after a full-suite run)
**Build source:** unaffected; `tests/` only.
**Level:** E4 live measurement — two **open questions**, one **correction to my
own work**, and no closed detection claim.

---

## 1. What was asked

`configs/Rules.json` ships 23 rules, three of them L4 with real rate
configuration:

```
R9006  TCP SYN Stealth Scan   L4  distinct_dst_ports 20 / 10000 ms
R9002  ICMP Flood             L4  count 50 / 1000 ms
R9007  TCP XMAS Scan          L4  per-packet FLAGS
```

`src/pipeline/event_processor.zig:307` evaluates them for
`ev.source == .capture_npcap`, and canonical Go-Nose frames map to exactly that
source. Does a SYN scan get tagged?

## 2. Measurements — and why the first answer was wrong

Run 1 (three trials): 150-port loopback SYN scan → **no** rule-tagged record;
across 1000 retained records, **none** carried a non-zero `rule_id`.

I wrote that up as "the rule path is empty". Then a full-suite run produced the
opposite: `test_a_syn_scan_is_tagged_by_an_l4_rule` **XPASSed**, i.e. a
rule-tagged record did appear — twice.

Checking the attribution rather than the verdict: the test counted *any* tagged
record, and the daemon also tags file and registry telemetry (R1001-style rules).
Restricted to sensor records (`npcap_sensor`), three scan rounds produced **zero**
tagged records and the test went back to xfail. So the XPASSes were almost
certainly file/registry detections, not the scan, and the claim narrows to:

* sensor records are not observed to carry an L4 rule hit under this stimulus;
* tagging elsewhere in the pipeline does work, which is worth knowing on its own.

The stimulus is also unproven: this install does not capture localhost traffic
(162 sensor records per 5 s idle vs 87 during the scan), so no trial can show the
scan reached the sensor.

Recorded as `DETECT-L4-001` (open, undetermined) and `CAPTURE-LOOPBACK-001`
(open, measurement limit). The earlier claim that the L4 path never tags was
withdrawn here rather than left in the record.

## 3. Two gates of mine were unsound — corrected

1. **`test_real_loopback_traffic_reaches_the_ring`** asserted `Packets captured`
   and ring records "do not go backwards". An idle host passes that, so the check
   could not fail. Replaced by `test_the_ring_keeps_accepting_records`, which
   reads the `forensic_records` counter twice and requires growth.
2. **Cursor-based measurement is unreliable here.** At roughly 700 records/s the
   ring retains about 23 s; `forensics list --after <cursor>` returns nothing
   once the cursor has rotated out, which made a guard test fail on a perfectly
   healthy daemon (head advanced 4225 records in 6 s). Every liveness claim now
   uses counters.

## 5. Limitations

1. **No detection verdict.** "Intermittent" is the whole finding; it does not say
   which of the three candidate causes (empty flags lane, rate-window keying,
   older installed binary) is responsible.
2. **Loopback is not captured**, so every scan-based number here is about the
   background traffic the sensor happens to see, not about the stimulus.
3. **No L7 claim.** R0056-style content rules need payload bytes on the canonical
   path; untested.
4. **23 rules, 1 host, 1 interface, one afternoon.** Nothing here generalises to
   a second host or a lab network.
