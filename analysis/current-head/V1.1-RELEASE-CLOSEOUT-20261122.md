## PR #38 CI finding and fix (2026-11-22)

Two red checks on PR #38 were the **same** `Package Release` job in the two
workflow runs triggered by the push, not two distinct defects. The job ran
`python tools/installer.py --package` on a clean runner without installing
`requirements.txt`; commit `3f92d3f` had added an Ed25519 import from
`cryptography`, which is listed in that file. `main` did not expose this because
its older version of the job only runs on tag pushes.

First fix: added `pip install -r requirements.txt` to the `Package Release`
job in `.github/workflows/ci.yml`. The next run then exposed a second, genuine
precondition: `tools/installer.py --package` fails closed when the owner-signed
`.sys` payloads are absent, and those payloads are deliberately **not tracked
in git**, so a clean CI checkout can never package an installer. The fail-closed
check itself is a security control (DRIVER-SIGN-PAYLOAD-001) and was **not**
weakened, faked, or supplied with unrelated binaries.

Final CI shape: every push runs `tools/installer.py --generate` plus a
non-empty script assertion and SBOM generation; the actual NSIS `--package`
step stays tag-only, where the controlled release environment must provide the
owner-signed payloads. A branch push therefore no longer claims to prove that
the installer binary builds — that claim belongs to the owner-run release,
which is already recorded and whose published bytes were re-verified above.
The `ci.yml` digest was re-stamped in `build_manifest.json` (same records-only
pattern as `7371d47`). Nothing in `SOURCE_PATHS`, the signed tree, or any
published asset changed; build source stays `a53eda8`. Local proof: manifest
674/674, `TRUTH_VALID`, `tests/release` 207 passed.
