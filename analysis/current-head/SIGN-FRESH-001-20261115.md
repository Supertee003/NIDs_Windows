# SIGN-FRESH-001 — the signature gate named the wrong tree, and could not tell

**Created:** 2026-11-15
**Build source:** `tools/final_audit.py`, `tests/release/test_release_board.py`,
`tests/tools/test_sign_release.py` — none in `RUNTIME_PATHS`, so the 24 h
window (`SOAK2-20261115`) stays valid.
**Level:** E2 (7 new pins against the gate evaluator) + E1 finding on the live board.

---

## 1. The finding

The release board read:

```
PASS  release_signature  [owner] release\T20-final\7234d7a\signatures.json
                                signs SHA256SUMS (BA861CB56EDF386D...) with a ed25519 key
```

but the tree rebuilt after `READY-PROMOTION-001` is `release/T20-final/9ebee9b`,
signed at `2026-11-15T16:13:36` over digest `9F87BF36…`. `RC-STALE-001` had
already written the rule the gate was supposed to enforce: *"The signature gate is
only meaningful for the tree that is actually shipped."* It was not enforcing it:

* `evaluate_signature()` walked the artifacts in **sorted path order** and
  returned the first complete signature. `7234d7a` sorts before `9ebee9b`, so the
  older tree won even though the newer one was signed, valid, and the one built
  from the patched runtime.
* Nothing compared the signed tree's commit with the runtime tree. `7234d7a` was
  signed before `7c604d5` existed, so it could not contain the lifecycle fix —
  the exact condition `RC-STALE-001` was raised to prevent.
* A **newer unsigned** release record would never be examined: the loop returned
  on the first valid older signature. Rebuilding an RC and forgetting to sign it
  would leave the gate green on the previous artifact.
* A **newer tampered** signature would also be invisible: the older pass was
  found first and returned.

All four are the same defect in different clothing: *"a signature exists"* was
being answered instead of *"the newest release tree is signed and current"*.

## 2. The rule now

`evaluate_signature()` selects the **newest release record** (by the commit's own
date, then by `signed_at`) and judges that one:

1. it must carry `signature`, `public_key` and `signed_digest` (a reference
   record is not a signature),
2. the `SHA256SUMS` beside it must exist and hash to `signed_digest`,
3. its `commit` must be in HEAD's history (`git merge-base --is-ancestor`),
4. the current runtime commit must be an ancestor of that commit, i.e. the
   signed tree contains the shipped runtime,
5. no fallback: if the newest record fails any check, the gate stays open.

`collect_release_facts()` now attaches `commit`, `commit_time`, `signed_at`,
`commit_in_history`, `commit_contains_runtime` and `runtime_commit` to every
record. A commit that git cannot place yields `None`, and the gate fails closed.

Verified on the live repository:

```
PASS  release_signature  [owner] release\T20-final\9ebee9b\signatures.json signs
                                SHA256SUMS (9F87BF36D28149F5...) with a ed25519 key;
                                commit 9ebee9b contains runtime 7c604d5
```

The old tree is still on disk, signed and intact; it is simply no longer the one
the board cites, because it is not the newest and does not contain `7c604d5`.

## 3. Pins

`tests/release/test_release_board.py` gained 7 tests (23 total in the file):

| Pin | Prevents |
|---|---|
| newest signed tree is judged, not the first path | the exact `7234d7a` vs `9ebee9b` regression |
| a signed tree that predates the runtime commit fails | a release that does not contain the shipped runtime |
| a signed tree whose commit is not in history fails | a signature over bytes from outside this history |
| a newer reference record blocks an older signature | rebuilding an RC, forgetting to sign, and shipping the old one |
| a newer tampered signature does not fall back | observing the first valid instead of the newest |
| unknown runtime ancestry fails closed | git unable to answer |
| (existing) digest mismatch / missing sums / reference record | the original fail-closed cases |

`tests/tools/test_sign_release.py` continues to assert against the gate's own
evaluator; its tmp tree is not a real commit, so it supplies the history fields a
current commit would have, and the history rules are pinned separately above.


## 4. Limitations, stated

1. The gate checks the **record**, not the cryptography: it never verifies the
   signature against the public key. `tools/sign_release.py --verify` does, and
   key custody remains the owner gate. The gate's job is to stop an *unsigned* or
   *stale* tree from being reported as shippable, not to replace verification.
2. `commit` is a field inside `signatures.json`. Someone who can rewrite the
   whole release tree can also rewrite it; the digest check then still has to
   match the `SHA256SUMS` they wrote. This is a release-process integrity check,
   not tamper-proofing against root.
3. `commit_contains_runtime` uses `RUNTIME_PATHS`. A change outside that set
   (`scripts/`, `tools/`, docs) after the release commit does not open the gate.
   That is deliberate — those trees do not change the running binary — but it
   means "current" here means "contains the current runtime", not "byte-identical
   to HEAD".
4. This does not close `release_signature` by itself; it makes the gate judge the
   artifact that exists. The gate is green because `9ebee9b` is signed and
   current, and it will turn red the moment a newer tree is built without a
   signature.
