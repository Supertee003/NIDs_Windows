# KIND-ATTR-001 — host telemetry stops masquerading as captured packets

**Patch ID:** KIND-ATTR-001
**Flow ID:** FLOW-INGRESS-KIND (minifilter/registry ingress → canonical event → queue kind → kind-based counters/correlators)
**Target HEAD:** `9e0d8626c647e6362244e64064ed9ebd195471b7`
**Date:** 2026-11-10
**Evidence level:** E2 (unit proof, `zig build test` exit 0). No E5 claim; no host run.

---

## 1. Defect

```
src/contract/canonical_event.zig:392   .event_type = .custom      // create() default
src/capture/minifilter_reader.zig:226  var ce = canonical.create(.minifilter);  // never sets event_type
src/contract/canonical_event.zig:321   EventType has no file/FIM member
src/pipeline/event_queue.zig:374       .custom => .packet_captured
```

Every minifilter FIM row (3.4 million kernel events drained in the current
diagnostic log) reached the pipeline as `EventKind.packet_captured`. Source
attribution stayed correct (`legacySourceFor(.minifilter) → .capture_fim`), which
is why per-source counters looked right while kind-based counting and any
kind-based rule saw host file activity as network traffic.

## 2. Chosen solution — provenance-scoped classification, no wire change

`EventKind.fim_change = 75`, `reg_change = 76`, `etw_process_create = 70`,
`etw_process_exit = 71` **already exist** in `src/contract/event.zig`. Adding a
new canonical `EventType` member would have required changing all six codecs and
the golden vector in one patch (AGENTS.md TEST HYGIENE #3). Reusing the existing
kinds needs none of that:

* the canonical event keeps claiming `.custom` — that is literally what a
  producer-specific record is — so `struct_size`, wire bytes, Go/C++/Python
  codecs and golden vectors are untouched;
* Zig is the sole detection authority, so it decides what `.custom` means from
  provenance that is already on the record (`source`, plus the reserved
  process-type byte the minifilter adapter writes through
  `hids.ProcessEventType`).

```zig
fn classifyCustom(ce: *const canonical.CanonicalEvent) event.EventKind {
    return switch (ce.source) {
        .minifilter, .file_sensor => switch (ce.reserved[canonical.RES_OFF_PROC_TYPE]) {
            @intFromEnum(hids.ProcessEventType.create) => .etw_process_create,
            @intFromEnum(hids.ProcessEventType.terminate) => .etw_process_exit,
            else => .fim_change,     // file_create and unknown ordinals fail toward files
        },
        .registry_sensor => .reg_change,
        else => .packet_captured,    // every other producer keeps the previous mapping
    };
}
```

The `else` arm is the risk control: a producer whose attribution has not been
measured keeps the exact previous behaviour, so this patch cannot silently relabel
another lane.

## 3. Old flow → new flow

```
OLD: kernel FIM record → canonical(.custom) → queue → packet_captured
     → packet counters inflated; FIM volume invisible to kind rules

NEW: kernel FIM record → canonical(.custom) → queue → classifyCustom()
       file_create/unknown → fim_change
       proc create/exit    → etw_process_create / etw_process_exit
       registry            → reg_change
       other producers     → packet_captured (unchanged)
```

## 4. Files changed

| File | Change |
|---|---|
| `src/pipeline/event_queue.zig` | import `hids`; add `classifyCustom()`; `.custom => classifyCustom(ce)`; new regression test |
| `tests` | the regression test lives in `event_queue.zig` (Zig test target) |

In scope: `.custom` → `EventKind` mapping and its test.
Out of scope: FIM/ETW duplicate preservation (the two lanes still report the
same file event; dedupe is a separate slice), any `EventType`/wire change, and
any consumer-side rule that now starts matching `fim_change`.

## 5. Invariant

A canonical record still carries `.event_type = .custom`; nothing on the wire,
in a codec, or in a golden vector changed. The only behaviour that changes is
which `EventKind` Zig assigns to a `.custom` record, and only for the sources
listed above.

## 7. Consequences and remaining work

* Packet counters for host telemetry stop being inflated after redeploy. The
  live daemon still runs the previous image, so **observed counters will not
  change until the host window** deploys `zig-out/bin/aegis_nids.exe`.
* E5 re-measure (FIM events visible as `fim_change`, packet count corrected) is
  pending the same host window; this record makes no host claim.
* Duplicate FIM/ETW lanes remain (unchanged by design). If correlation later
  consumes both, a dedupe slice is required.

## 8. Risk / rollback

Risk: a consumer that previously relied on `.packet_captured` for minifilter
rows (none was found in production correlator rules — the DNS classifier comment
at `event_queue.zig:339-347` records the same "dead kind" pattern) would change
behaviour. Rollback: revert the three hunks in `event_queue.zig`; no state,
schema, or wire artefact is involved.
