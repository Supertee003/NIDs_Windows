## 1. What the gap said, and what was wrong with the question

`DETECT-L4-001` (2026-11-14) opened because three rounds of a **150-port loopback**
SYN scan produced no rule-tagged `npcap_sensor` record:

* loopback is not captured by this install — 162 sensor records per 5 s idle vs 87
  during the scan (`CAPTURE-LOOPBACK-001`);
* so the scan never provably reached the sensor, and the three candidate causes
  (empty flags lane, rate-window keying, older installed binary) were never
  separated;
* a later XPASS was traced to file/registry detections, not to the scan.

The gap's own `next_step` said "run the scan on a lab interface (VMnet) rather
than loopback". That was the right instinct and the wrong interface: this install
opens **Wi-Fi**, not VMnet (`LAB-WIFI-001`, commit `a862985`).

## 2. The chain the stimulus has to cross

| Hop | Current-HEAD evidence |
|---|---|
| Nose attaches bytes | `nose/capture.go:captureAttachment` — v3 envelope, bounded to `EventV3MaxPayload = 1024` |
| Nose attaches TCP flags | `ContextFlags` transport lane (DEPLOY-131), read back by `canonical.getTcpFlags` |
| Zig attributes the frame to the sensor | `event_queue.zig:480` `ev.source = legacySourceFor(.npcap_sensor)` → `.capture_npcap` |
| L4 rules run | `event_processor.zig:307` requires `ev.source == .capture_npcap` — satisfied by the hop above |
| R9006 semantics | `configs/Rules.json`: `layer L4`, `match_pattern FLAGS:S`, `rate_mode distinct_dst_ports`, `rate_threshold 20`, `rate_window_ms 10000` |

So the rule needs **≥ 20 distinct destination ports from one source inside 10 s**,
with TCP SYN flags intact. The loopback test could never supply that on this host;
a scan over the sensor's own link can.

The attributed row, read from `C:\Windows\System32\logs\aegis_core.ndjson`:

```
2026-11-15T17:07:45.820Z  signature_match  rule 1745456278  src 192.168.1.39  sport 59773
```

source/window, and it only emits when one source has touched 20 *distinct* ports
inside 10 s. The 40 SYNs crossed that threshold mid-loop and the row landed 1.8 s
after the window opened.

## 4. Negative control — and the reason its verdict is not the control

```powershell
python tools\lab_attack_window.py --label l4-testnet-negative-20261116 --seconds 45 --expect-src 192.168.1.39
# 10 SYNs to 192.0.2.1 ports 1..10, 0.58 s
```

Artifact:
`admin-evidence/lab-l4-testnet-negative-20261116/attack-window-20261115T171024Z.{json,md}`.

| Fact | Value |
|---|---:|
| frames gained | +16,107 |
| **R9006 rows** | **0** |
| R9006 threshold crossed | no — 10 ports < 20 |
| dropped / shed / quota_shed | +0 / +0 / +0 |

The tool's own verdict for this run is `PASS`, and that PASS must **not** be read
as a detection of the control: one ambient row matched the host's own outbound TLS
session (`rule 2485705370`, sport 51568, 1024-byte attachment). `--expect-src`
can only see `src_ip == 192.168.1.39`, and in a control fired *from* the victim,
the victim's ordinary traffic wears the same source. The control is the **per-rule
table**: `R9006 = 0`.

That ambient row is not noise to be waved away — see §5.

## 5. Adjacent finding: the AC matcher applies process rules to wire bytes

`event_processor.zig:280` runs the Aho-Corasick matcher over `qe.payload` for every
source except `capture_host_net`, and it never consults the rule's `layer`.
`R2003` is a `KERNEL_PROCESS` rule whose pattern is `IEX|DownloadString|…`; a
three-byte token inside an encrypted TLS record therefore becomes a
"PowerShell Cradle Download" detection. 366 rows, 291 of them inbound HTTPS from
`src_port 443`, all `enforcement_status: observed`, `host_effect_confirmed: false`.

This is alert quality, not host authority: the gate is closed, no receipt, no
filter, no effect. It is recorded as a new gap, `RULE-LAYER-SCOPE-001` (P3, v1.1
because the fix is a `src/` edit and would reopen the soak). It also explains why
the proof leans on the rule identity and its rate semantics rather than on "a row
appeared with our IP on it".

## 6. The soak-window deviation — stated before the claim

This proof ran at `00:07–00:10` local, inside `SOAK2-20261115`
(`2026-11-15T16:50:31` → `2026-11-16T16:50:31`). The declaration
(`analysis/current-head/SOAK2-20261115.md`) said:

> Running `tests/integration/` or a 150-port scan **inside** this window will shed
> again. … Nothing in this session will run live gates before 2026-11-16T16:50.

What actually ran: a 40-port SYN burst (75 s window) and a 10-port control (45 s),
both to TEST-NET, both from this host, no service restart, no `src/` edit, no VM.
Measured cost from the artifacts:

| Counter | Delta across both windows |
|---|---:|
| `dropped_total` | **0** |
| `shed_overload` | **0** |
| `source_quota_shed` | **0** |
| `depth` after | 0 |

At 7.42 h the soak gate reports `problems []`, `scm_restarts []`, 1,387/3,500
drops, 0/20,000 shed.

The honest reading:

1. The **declared invalidation criteria** (budget breach, uptime gap, restart) did
   not fire. The burst cost nothing measurable, so the 24 h loss result is not
   weakened by it — if anything the window now covers a 7× frame-rate burst with
   zero network loss.
2. The **letter of the declaration** is broken: the window no longer has "no gate
   activity by design", and the closeout must say so instead of quoting the
   sentence as if it held.
3. Whether that is acceptable is an **owner decision**, not a silent one. The
   alternative is a third window started at `00:15` (closing 24 h later). This
   record does not pretend the choice was made in advance.

**Owner decision (2026-11-16, ~00:25 local): keep the window.** The numeric
criteria hold, both bursts cost zero drops and zero shed, and the deviation is
recorded here; the soak closeout must carry this decision and this paragraph
rather than describing the window as pristine. No further scan, live gate or
full test runs before `16:50:31`.

The 1,387 drops that *do* count against the budget appeared **before** this proof
(the "before" snapshot of the positive window already reads 1,387) and are all
`capture_etw` source-quota drops, not `capture_npcap`. They are the subject of the
soak closeout, not of this detection claim.

## 7. What this closes, and what it does not

**Closes `DETECT-L4-001`:** on the path the release actually ships, with the
installed binary, a real ≥ 20-port SYN burst is tagged by R9006, and a 10-port
stimulus below the threshold is not. The loopback silence was a property of the
stimulus, not of the rule path.

**Does not prove:**

1. **A remote attacker.** The source is this host. R9006 keys its rate window on
   the source address, and nothing in the path depends on the source being local —
   but a Kali VM scanning this host was not run (that is `RB-022`, post-soak).
2. **R9002 or R9007.** Only R9006 was exercised.
3. **L7.** SYN-only probes carry no application payload; `IDS-L7-003` remains open.
4. **Any host effect.** All rows are `observed`; the detection-only invariant was
   read live from `aegisctl.py enforce status` in this session and is unchanged.
5. **The `flows_active` 4,092 → 94 movement** observed across the positive window.
   The flow table is not a loss path and both queue depth and drop counters stayed
   at 0, but the cause was not measured and is not claimed.
