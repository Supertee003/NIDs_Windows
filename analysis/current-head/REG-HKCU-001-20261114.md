# REG-HKCU-001 — watch user hives, name the registry rules, keep the key path

**Created:** 2026-11-14
**Build source before this patch:** `cc3518d`
**Finding:** the HKCU Run canary produced no alert, and the registry alerts that
did fire were `UNKNOWN_RULE` with `payload_len=0`.
**Level:** E2 (unit/build). The host canary is the E5 gate.

---

## 1. Three defects behind one silent canary

### 1.1 The native watcher only opened HKLM roots

`RegistryMonitor.startAll` opened exactly two keys:

```
HKLM\SYSTEM\CurrentControlSet\Services
HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Run
```

The code comment said rules outside HKLM "remain eligible for trie matching",
but eligibility without a watcher means no event. `HKCU\...\Run` had no
watcher, so rule 3 could never fire.

### 1.2 A SYSTEM service cannot use HKCU

AEGIS runs as `LocalSystem`. `HKEY_CURRENT_USER` in that token is SYSTEM's
hive, not the interactive user's. Watching `HKCU` directly would watch the
wrong user. The fix must enumerate `HKEY_USERS\<SID>` for the loaded hives.

### 1.3 The record carried no key path

`registryThread` pushed every registry event with an empty payload:

```zig
_ = queue.pushEvent(ev, &[_]u8{});
```

So the forensic record said `payload_len=0` and no operator could tell which
key matched. The alert also fell back to `UNKNOWN_RULE` because ids 1/2/3 are
the native monitor's own numbers, not catalog FNV hashes.

## 2. What changed

`src/windows/registry_monitor.zig`:

- `MAX_WATCHERS` 8 -> 32; each watcher now owns an **event path** (what
  changed, e.g. `HKU\<SID>\Software\...\Run`) and a **match path**
  (normalized `HKCU\Software\...\Run`).
- `startAll` opens the two HKLM roots, then `watchUserHives()` enumerates
  `HKEY_USERS` with `RegEnumKeyExA` and opens
  `<SID>\Software\Microsoft\Windows\CurrentVersion\Run` for every loaded hive.
- `observeMatch(kind, event_path, match_path)`: the trie matches the normalized
  path, the record keeps the SID for attribution. `observe()` stays as the
  single-path wrapper used by tests.
- `pollNative` passes both paths and re-arms the same handle.

`src/pipeline/telemetry_threads.zig`:

- registers rule 3 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`;
- carries the key path as the event payload
  (`reg_ev.path[0..path_len]`) instead of an empty slice.

`tools/aegisctl.py` (ALERT-MAP-001):

- maps native ids 1/2/3 to `REG-HKLM-RUN`, `REG-HKLM-SERVICES`,
  `REG-HKCU-RUN` with severity High, so the alert surface no longer says
  `UNKNOWN_RULE` for them.

```

```

## 4. What this does not fix

- **E5 pending:** the host must run the new build and a HKCU Run canary must
  produce `REG-HKCU-RUN` with the SID-bearing payload.
- **Startup-time enumeration:** a user hive loaded *after* the registry thread
  starts is not watched until restart. Logon-time monitoring needs a re-scan
  (or the ETW lane).
- **500 ms poll:** a canary can take up to half a second to reach the queue;
  query after ~1 s, not 0.5 s.
- **Event path is the watched root,** not the exact value name (RegNotify does
  not report the value). Rule 3 means "something under the user's Run key
  changed", which is the persistence signal.
- **Forensic retention** is unchanged (~16k records); the canary must be
  queried promptly.
- **ETW registry paths** (`\REGISTRY\USER\<SID>\...`) are still not normalized
  into this rule path; the native watcher is the authority for registry rules.
