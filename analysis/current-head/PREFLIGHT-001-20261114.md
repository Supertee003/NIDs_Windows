# PREFLIGHT-001 — one command that answers the clean-host gate

**Created:** 2026-11-14
**Build source:** `68a6caa` (this patch adds `tools/` + `tests/`)
**Level:** E2 (10 pure-function pins) + one live run on the lab host
**Closes the runbook gap left by:** `INSTALLER-BOOT-MODEL-001` (E2) and
`RC-FINAL` §3 item 5

---

## 1. The gap

`INSTALLER-BOOT-MODEL-001` made both installers ship the boot model:

- `AegisNids` created `start= demand`,
- `AegisBootSequence` registered (AtStartup, SYSTEM, 20 s delay),
- `AEGIS_LOSS_BUDGET=3500` written into the service environment,
- setup aborts if the task install fails.

Its own E5 gate was written as six things to check after a reboot: services
RUNNING, task present, budget present, loader ran, ring 0, daemon healthy. Six
commands, remembered by a human, on a machine that is by definition fresh — the
same shape of check that produced the 2026-11-11 boot failure in the first place
(the host was "obviously fine" because the services were RUNNING).

## 2. What this adds

`tools/host_preflight.py` reads the host and emits a JSON verdict:

| Check | Failure mode it catches |
|---|---|
| `service_start_type` | `AUTO_START`: SCM starts the daemon before the demand-start drivers, the ring fills with no reader, the daemon is degraded from its first second (448/4,012 rows on 2026-11-11) |
| `service_loss_budget` | budget missing from the service environment (health will then use the strict default) |
| `boot_task_present` / `boot_task_system` / `boot_task_last_result` | task absent, disabled, running as the wrong principal, or exited non-zero — a loader that failed started nothing, whatever `sc query` says |
| `boot_task_loader_installed` | the loader is not `<install dir>\scripts\boot-sequence.ps1`, i.e. the host was hand-fixed from `admin-evidence` instead of installed |
| `driver_AegisWfp` / `driver_AegisMinifilter` | a driver that did not come up |
| `daemon_health` / `daemon_loss_budget` | daemon DEGRADED, or reporting a different budget than the service |
| `minifilter_ring_clean` | `minifilter_ring_dropped != 0`, the ring loss a late reader causes |
| `daemon_uptime` | daemon younger than the window (optional floor; proves the boot loader, not a human, started it) |

Every value is read from `sc.exe`, `reg`, `schtasks` or the control pipe, and an
unreadable value is a **failure**. No check can pass by being absent.

## 3. Live run on this host (the discriminating case)

```
verdict FAIL  failed ['boot_task_loader_installed']
PASS service_start_type        AegisNids START_TYPE is DEMAND_START
PASS service_loss_budget       AEGIS_LOSS_BUDGET is 3500 (expected 3500)
PASS boot_task_present         AegisBootSequence exists=True state=Enabled
PASS boot_task_system          AegisBootSequence runs as SYSTEM
PASS boot_task_last_result     AegisBootSequence last result 0
FAIL boot_task_loader_installed loader is ... D:\NIDs_Windows\admin-evidence\host-window-003-20261010\boot-sequence.ps1
PASS driver_AegisWfp           RUNNING
PASS driver_AegisMinifilter    RUNNING
PASS daemon_health             state=RUNNING degraded=False
PASS daemon_loss_budget        health loss_budget is 3500 (expected 3500)
PASS minifilter_ring_clean     minifilter_ring_dropped is 0
PASS daemon_uptime             daemon uptime 121.2 min
```

This is the result that makes the tool worth having: eleven checks pass, and the
one that fails names exactly the thing that is true — this host was hand-fixed
from `admin-evidence`, so it is not evidence that a *fresh install* works. A gate
that could not tell those apart would let us close the E5 installer item on a
machine that never ran the installer.

Artifact: `admin-evidence/host-window-006-20261111/preflight-20261114.json`.

## 5. What this does not prove

- **Not E5.** The E5 claim still requires a clean Windows host: install from
  `aegis-installer-5.0.0.exe`, reboot, then run this tool with
  `--min-uptime-min 5` and keep the JSON. That run has not happened.
- The tool reports the host it is run on; it cannot distinguish "fresh install
  on a clean image" from "install over an old one". The upgrade path is still
  untested (recorded in `INSTALLER-BOOT-MODEL-001` §4).
- It does not check file hashes of the installed binaries. `tools/stage_helpers.py
  --check` and the deploy scripts do that; duplicating it here would give two
  sources of truth for the same digests.
