# FREEZE-001 — Code freeze and release gate checklist

**Created:** 2026-11-09
**Purpose:** define when the tree is frozen and what must be true before a
release candidate may be cut. Every item is a command with an exit status or a
number, not a judgement.

---

## 1. Freeze rule

A **freeze** begins when a release candidate is cut and ends when it is either
released or abandoned. Between those points:

1. No commit may touch `SOURCE_PATHS` (`tools/truth.py`). A release candidate is
   identified by its build source commit; if that commit moves, the candidate is
   void and a new one is cut.
2. Records-only commits are allowed (evidence, maps, docs) and must keep
   `truth.py verify` green.
3. Any defect found during the freeze is fixed in a new candidate, never patched
   into the frozen tree.
4. The frozen candidate is archived with its hash before testing begins.

## 3.1 Declared limitations (this is the R-09 exit record)

These ship as stated limitations, not as solved problems. They are the release
notes for the current build (`a8f3abf`, installed image
`D39A1D2CC6CEE76FA0AE35EBB0B497319FA252AC18C1285F408F3E8490925C90`).

1. **No production signing custody.** The kernel drivers are test-signed: the WFP
driver by `CN=AEGIS NIDS Test Signing` (`00E92849867308596564D134BB981EF726798E97`),
the minifilter by `CN=AEGIS Test Signer` (`60B05537FEB7A40D6F6624FF5C005C09DC245A63`).
Kernel load therefore depends on the host trusting those certificates or on test
signing being enabled. This is a lab trust chain, not a shippable one.
2. **Runtime binaries are unsigned.** `install_aegis.ps1` prints that warning on
every install (6 binaries); their integrity is covered by the bundle manifest
hash comparison, not by Authenticode.
3. **E7 is unreachable until custody exists.** Release verification (E7) requires
a signature a customer can validate; the highest level this tree can honestly
claim today is E5, plus the one E7 artifact already recorded under the old
assumption.
4. **No timestamping and no EV/attestation signing.** Nothing here produces a
signature that survives certificate expiry as a release artifact.
5. **The deployed host is a lab host.** The window 002 results (parity, driver
load, WFP audit, refusal, rollback, soak) were measured on one Windows machine
with a test cert; they do not establish fleet behaviour.

## 4. What this checklist cannot do

1. It cannot make a release signed: without key custody, E7 stays a declared
   limitation.
2. It cannot prove kernel behaviour by inspection: items 21–25 were run under
   elevation in window 002, and three of them are still open because they need
   time rather than a command — a reboot (22), a 24 h soak (24) and a full
   install/rollback/reinstall cycle (25).
3. It cannot replace review: a green checklist means nothing contradicted the
   evidence, not that nobody was wrong.
