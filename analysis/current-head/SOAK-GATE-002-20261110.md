So the deploy and the dedupe are real, and the run also produced a real,

3,229 op-sets/s; it has moved up, but 6,383 is still above it.

## The defect (why the verdict was false)

`soak_rate.py` shipped in `admin-evidence\` (untracked) and had two defects:

1. **It never held the rate.** `--ops-per-second` was a label only; three
   workers ran free. The window labelled "4,000/s" measured 6,383/s.
2. **It read the wrong key.** Attribution looked for `queue.stats.buckets` /
   `.sources`; the daemon publishes `by_source`. The absent key produced an
   empty dict, so `drops_total = sum({}) = 0` and `zero_drops` was always true.

Both are the same class of failure that GATE-HONESTY-001 was meant to remove:
a green result produced by the checker, not by the system. The window-004
`zero_drops: true`, its `rate_exit: 0`, and the `soak-window-start.json` marker
are therefore **retracted**; the soak cannot be evaluated against this window.

The cumulative counters recorded in the same run are the truthful record:
`queue_dropped_total=80,270`, `minifilter_pipeline_dropped=78,096`,
`minifilter_ring_dropped=0`.

## Fix

The tool now lives in the tracked tree and is pinned by tests:

| File | Change |
|---|---|
| `tools/soak_rate.py` | New tracked measurement tool (replaces the untracked copy) |
| `tests/tools/test_soak_rate.py` | 8 tests: bucket parsing, absent-schema failure, delta, verdict, held-rate failure |

Corrected contract:

1. Every worker is throttled to `target / workers` per second; the reported
   rate is the held rate.
2. `by_source` is parsed; **absence is an attribution failure (exit 2)**, never
   zero drops.
3. A window passes only when the per-source delta **and** the `data_integrity`
   delta are both zero.
4. Cumulative counters are written next to the deltas so a dirty window is
   visible.
5. Exit 0 = pass, 1 = measured fail, 2 = unattributable fail.

## Invariant

No run of this tool can report `zero_drops: true` while either counter family
moved, and no run can report a rate it did not hold.

## 6. Result — first honest held-rate run, and what it forced

The corrected tool was first exercised against the window-004 daemon (already
deployed, cumulative counters dirty, so only deltas are meaningful):

| Run | Held rate | New drops | Attribution |
|---|---|---|---|
| 10 s smoke, 3 workers | 3,657.6/s | 0 | ok |
| 10 s smoke, 6 workers | 3,990.9/s | 0 | ok |
| **90 s, 6 workers** | **3,887.5/s** | **20,430** (`capture_fim 19,700`, `capture_etw 730`) | ok |

The 90 s window is a real FAIL, and it changed the diagnosis:

- `queue.stats` reports `source_quota_shed = 100,700` and
  `reserved_tail_shed = 0`, `depth_peak = 13,621 / 16,384`.
  The loss is **not** total-queue exhaustion and **not** consumer starvation:
  it is the per-source share (`SOURCE_OCCUPANCY_CAP = WORKING_HOST_TAIL / 2`)
  refusing the FIM lane while the other half of the host tail sits unused.
- After ETW-FILE-DEDUPE-001 the duplicate lane is no longer the loser: the
  minifilter lane is. The ceiling moved up (3,229 → somewhere above 3,887) but
  has not reached 4,000.

So #29 is still open. It needs one more, bounded change: the minifilter reader
must pace its own burst instead of overflowing its share (see §7).

## 7. PACE-MF-001 — pace the pull loop instead of dropping

| File | Change |
|---|---|
| `src/pipeline/event_queue.zig` | `sourceOccupancy()` read-only view of `g_ingress_active` |
| `src/capture/minifilter_reader.zig` | `shouldPace()` + `paceToShare()`: while within `PACE_MARGIN` of the cap, wait 1 ms (max 5 ms per record) and retry; the kernel ring is the buffer |
| `src/pipeline/runtime_state.zig` | `g_fim_pace_waits` counter |
| `src/control/handler_registry.zig` | root `minifilter.pace_waits` published; test pins it |

Why this is the right shape:

- The reader is a **pull** model; the kernel ring already buffers. Pausing is
  strictly better than a refused push, which is an unrecoverable loss.
- The wait is bounded (5 ms/record) and the ring's own `dropped` counter proves
  whether the pause cost anything. A stuck consumer therefore still ends in a
  counted drop, never a hung reader.
- Isolation is preserved: the pacing source stops at its own share, it does not
  consume another sensor's half.
