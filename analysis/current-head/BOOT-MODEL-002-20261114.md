# BOOT-MODEL-002 — the boot loader's verdict was "reached its last line"

**Created:** 2026-11-14
**Level:** E2 (5 pins, two of them behavioural against a `sc.exe` stub)
**Same shape as:** SERVICE-EXISTS-001 — a decision made from text where the exit
code is the fact

---

## 1. Two defects, one class

`scripts/boot-sequence.ps1` ended with an unconditional `exit 0`. The task's
Last Result is written to the probe and read by `tools/host_preflight.py` as
`boot_task_last_result == 0`; with the unconditional exit, that check measured
"the script reached its last line", not "the stack came up". A boot where
`AegisWfp` never loaded reported success, which is precisely the condition the
probe exists to catch.

`scripts/install-boot-task.ps1` decided that `sc.exe config AegisNids start=
demand` had succeeded by matching `FAILED|denied` in its output. `sc.exe`
localises its messages, so on a non-English host a real failure can produce text
that matches neither word; the script would then log `AegisNids START_TYPE =
DEMAND_START` over a service it never changed, leaving AUTO_START and the
2026-11-11 boot order in place.

## 2. What changed

- `boot-sequence.ps1` computes `$ok` from all three services (`AegisWfp`,
  `AegisNids`, `AegisMinifilter`), records it in `post-boot-probe.json`, logs the
  per-service state when it is false, and exits 1. `-StartAttempts`,
  `-StartDelaySeconds` and `-ReadyWaitSeconds` exist so a test can shorten the
  retry window; the scheduled task action passes none of them, so production
  behaviour is unchanged.
- `install-boot-task.ps1` judges `sc config` by `$LASTEXITCODE` and reports the
  code in the thrown message.

## 3. Verification

| Check | Result |
|---|---|
| `python -m pytest -q tests/release/test_boot_model_scripts.py` | 5 passed |
| behavioural: `sc.exe` stub returns RUNNING | exit 0, `probe.ok is true`, all four services RUNNING |
| behavioural: `sc.exe` stub returns STOPPED | exit 1, `probe.ok is false`, log says the stack is NOT up |
| structural | no `$out -match 'FAILED|denied'`; `if (-not $ok)` precedes the final `exit 0` |

The behavioural pins run the real script under a PowerShell function that shadows
`sc.exe`, with `PROGRAMDATA` redirected to `tmp_path`, so no service is touched
and nothing is written to the tracked tree.

## 4. Limitations

1. **E2, not E5.** The exit code the *scheduled task* records was not re-read
   from Task Scheduler after a real boot; that needs the owner's reboot window.
   The script's own exit code is proven.
2. **The stub is not `sc.exe`.** It reproduces the two fields the script parses
   (`STATE : 4 RUNNING|STOPPED`) and nothing else.
3. **`install-boot-task.ps1` is judged structurally only.** Its `sc config` runs
   elevated against a real service; the E2 pin checks that the decision is the
   exit code, which is the property that was wrong.
4. **`boot_task_loader_installed` stays FAIL on this host** — the boot task still
   points at `admin-evidence\...\boot-sequence.ps1` rather than
   `C:\Program Files\AEGIS NIDS`. This patch does not change that; it is the
   `clean_host_e5` gate in `tools/final_audit.py --release-check`.
