# SOAK-SHED-001 — the 24 h window is invalid, and my own gates invalidated it

**Created:** 2026-11-14
**Build source:** unaffected.
**Level:** E4 live measurement + a process finding.

---

## 1. What the soak says now

```
$ python tools/host_soak_check.py --start 2026-11-14T22:20:15 ... --hours 24
verdict        FAIL
elapsed_hours  16.95
problems       ["shed_overload grew by 15163 inside the window (baseline 0,
                 now 15163) exceeding the policy-shed budget 4000"]
scm_restarts   []
```

`dropped=0` throughout, every loss counter 0, no service restarts — the
invariant that matters held. What moved is `shed_overload`: the queue refused
15,163 events at admission (0.2 % of 7.4 M pushed).

For 60 s after the failure it stayed at exactly 15,163 while the pipeline kept
pushing ~280 events/s, so this was a **burst**, not ongoing pressure.

## 2. What caused the burst

The burst coincides with operator-generated adversarial load inside the window:

* the `E6-BURST-001` gates (150-port scans, repeated);
* the `DETECT-L4-001` probe rounds (three more scans per run, several runs);
* a full-suite regression run at HEAD (1,377 tests, five minutes of load).

That load is what a detection product is supposed to survive, but 15,163 sheds
is 3.8× the declared budget, and the tool is right to fail the window.

## 3. The process finding — this is the part worth keeping

**Live gates and a 24 h soak cannot share a host window.** `tests/integration/`
talks to the same daemon the soak measures, so an adversarial gate run *is* soak
load; whichever runs second invalidates the first. The window was started, then
the gates were built and run inside it, and the window paid for that.

Two acceptable orders, and nothing else:

1. gates first, then a clean window with nothing else running; or
2. a window that declares the gate runs in advance and re-baselines after each,
   with the shed budget sized for them (15,163 observed, so 4,000 was optimistic).

## 4. What this changes

1. **The 24 h soak evidence is not usable as a clean-host result.** It must
   restart from a new baseline. The owner waiver in `docs/gates/waivers.json`
   becomes moot for this window: the gate is not "not run", it is "run and
   failed", which no waiver should paper over.
2. **The constraint that blocked `src/` changes has lifted** — not because the
   soak passed, but because the window it protected is now invalid. The three
   prepared patches (`POST-SOAK-PATCHES-20261114.md`) can proceed, and the fresh
   window should start *after* they land and the daemon is reinstalled.
3. **One of my gates was wrong about the contract.** `test_the_pipeline_drops_nothing_while_it_runs`
   asserted `shed_overload=0`. Shedding is the designed admission response under
   overload — the soak tool is what budgets it — so the test now asserts the real
   invariant (`dropped=0`, the silent loss) and parses the shed counter instead of
   pretending it cannot move.

## 5. Limitations

1. **No timestamped shed history** — the counter is cumulative, so "the burst was
   my load" is inferred from timing and from the counter being flat afterwards,
   not from a log line.
2. **The 4,000 budget is unvalidated** for any load that includes adversarial
   gates; a fresh window with gates will need a justified number.
3. **Nothing here says the daemon is unstable.** No restart, no drop, no error
   counter moved; admission control did its job loudly.
4. **The failed window still tells us something**: 16.95 h with `dropped=0`, all
   loss counters 0, no restarts, under a load that included my own scans.
