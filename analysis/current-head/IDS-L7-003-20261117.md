## 2. Why the blocker could be closed without a restart

`IDS-L7-003` was written when only direct Npcap carried full Ethernet bytes.
That premise stopped being true at wire v3:

- `nose/capture.go:captureAttachment` attaches up to 1,024 bytes of the
  captured frame plus a provenance envelope (`EventV3MaxPayload`);
- `src/capture/nose_pipe_reader.zig` forwards the v3 payload to the pipeline;
- `src/pipeline/event_queue.zig:322` maps canonical source `npcap_sensor` to
  `.capture_npcap`, which satisfies the anomaly lane's source guard at
  `src/pipeline/event_processor.zig:341`.

So the canonical Nose path can raise L7 anomalies on its own. No lab-interface
pin, no service restart, and no soak-window break were needed. The anomaly
lane still refuses to write `matched_rule_id`, so these events cannot reach
policy, PEP, or `ActionDispatcher` — they are evidence only.

The comment at `src/pipeline/event_processor.zig:335` still asserts the old
"direct Npcap is the only ingress with a full Ethernet payload" premise. It is
stale; correcting it is a `src/` edit and therefore v1.1 work, not part of this
release (same reasoning as `RULE-LAYER-SCOPE-001`).

## 5. Two rows per request: measured, attributed to the capture layer

Every single malformed request produced **two** anomaly events. They are
distinct events, not a duplicated log line:

- distinct `event_id`, `audit_id`, `trace_id` and IDS receipt sequence;
- same `src_ip`, same `src_port`, same rule;
- `mono_ns` identical or up to ~0.5 ms apart.

A control capture on the same Wi-Fi device with a single `dumpcap` handle
(`-p`, no promiscuous mode, filter `tcp port 45007`) showed **every frame
twice**, including the SYN, the payload and the FIN:

```
frame 6  1794857969.424380500  ip.id 0x29fb  seq 1  len 18  GET / HTTP/1.1..
frame 7  1794857969.424387500  ip.id 0x29fb  seq 1  len 18  GET / HTTP/1.1..
```

Same `ip.id`, same TCP sequence, same bytes, ~7 µs apart, one interface in
the file, Ethernet encapsulation. A retransmission would not reuse `ip.id`
and would be milliseconds or seconds later, not microseconds.

Controls and code checks rule out the product:

- A capture on the VMware VMnet1 adapter during three pings showed three ARP
  requests, **no duplication** — so this is not generic Npcap behaviour.
- `nose_frames_read` and `nose_frames_submitted` move together (718/718 in a
  short probe), `nose_duplicate_event_ids=0`, `nose_non_monotonic_event_ids=0`.
- `nose/capture.go:154-183` emits exactly one event per `ReadPacketData`
  result, and `src/capture/nose_pipe_reader.zig:427` pushes exactly one frame
  per pipe frame.

Conclusion: on this host the Wi-Fi adapter/Npcap path delivers each frame
twice to every capture handle. AEGIS is processing what it was given. The
duplicate is recorded as gap `CAPTURE-DUP-WIFI-001` (P3, environmental), and
**the effective anomaly count on this adapter is half the row count**.

## 6. Row-level evidence and what it does not carry

All eight attacker rows (2 + 6) carry:

```
event=protocol_anomaly  src_ip=192.168.1.207  enforcement_status=observed
host_effect_confirmed=false  policy=pass  level=warn
ids_receipt_version=1  ids_receipt_sequence=<monotonic>  ids_receipt_hash=<sha256>
```

The log projection does not emit `dst_ip`, `dst_port` or `proto` for any
event kind (a sample `signature_match` row has the same field set), so the row
proves *who* and *which rule*, not *which service port*. `payload_len` is the
full frame length (84 bytes), not the L7 payload length. The forensic ring and
the receipt hash are the durable evidence; the NDJSON row is the operator
projection.

## 7. Limits — stated, not implied

1. **One host, one VM, one adapter.** Killer Wi-Fi AX1650i + Npcap on this
   Windows host only. The duplicate-frame behaviour is adapter-specific.
2. **Three rules of the slice.** `10004`, `10001`, `10003` fired. `10002`
   (URI > 8192), DNS checks (`10005`/`10006`), TLS checks (`10007`/`10008`)
   and SMB checks (`10009`/`10010`) were **not** exercised live.
3. **Single-segment requests.** The parser reads one TCP payload; no
   reassembly is claimed or tested. A request split across segments was not
   sent.
4. **IPv4 only.** No IPv6 stimulus.
5. **The victim is a lab listener** (`python -m http.server 8080`), not a
   production application. The point is the sensor path, not the service.
6. **Counts must be halved** on this adapter because of
   `CAPTURE-DUP-WIFI-001`. Detection correctness is unaffected; evidence
   volume is inflated.
7. **No enforcement claim.** Every row is observe-only; this run says nothing
   about policy, PEP, or host effects. `prevention_gate` stayed closed.
8. **No release re-certification.** The runtime was not rebuilt, reinstalled,
   restarted, or re-signed. Build source remains `7c604d5`, the signed release
   tree is unchanged, and the running 24 h process window was not interrupted.
